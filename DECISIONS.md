# DECISIONS

Решения, которых нет в ТЗ или которые от него отступают. Формат: что решили → почему.

## D-001. Рабочая копия и хранение репозитория
К проекту не подключён GitHub. Код живёт в git-репозитории; после каждого этапа он синхронизируется
в общую папку проекта `/mnt/project-files/happy-steps` (вместе с `.git`, без `node_modules`/`.next`).
→ Работа сохраняется между сессиями; push/деплой — когда появится репозиторий и аккаунты.

## D-002. Локальный Supabase без Docker
В среде разработки недоступны Docker-образы (лимит реестров). Поэтому `scripts/local-supabase` поднимает
системный Postgres 16 + официальные бинарники Supabase Auth (GoTrue v2.180) и PostgREST v12 + небольшой шлюз
на `:54321` с эмуляцией Storage и Realtime. Код приложения не знает об этом — он ходит в «обычный» Supabase.
С Docker используется штатный `supabase start` (`supabase/config.toml`), миграции те же.
→ Эмуляция Storage/Realtime покрывает только то, что использует приложение; на проде — настоящий Supabase.

## D-003. Next.js 16 без cacheComponents
`create-next-app` включает `cacheComponents`. Приложение почти целиком персональное (cookies, RLS),
поэтому оставлен классический динамический рендеринг. `output: "standalone"` — для Docker-образа.

## D-004. Вход по телефону через технический e-mail
Phone-провайдер Supabase Auth в облаке требует подключить SMS-провайдера. ТЗ это допускает (§4):
пользователь создаётся через admin API с e-mail `<цифры телефона>@<AUTH_EMAIL_DOMAIN>` и `email_confirm: true`,
вход — `signInWithPassword({ email, password })`. Пользователь видит только телефон; телефон хранится в `profiles.phone` (уникален).

## D-005. Ограничение частоты входа
Собственная таблица `login_attempts`: не больше 5 неудачных попыток на номер (и 25 на IP) за 15 минут.
Проверка в server action до обращения к Auth. Встроенные лимиты GoTrue остаются вторым рубежом.

## D-006. Компоненты в стиле shadcn/ui написаны вручную
Реестр shadcn недоступен из среды. Компоненты (`src/components/ui`) написаны в той же манере поверх `radix-ui`,
`class-variance-authority`, `tailwind-merge` — их так же можно менять как свой код.

## D-007. Шрифт Manrope self-hosted
`@fontsource-variable/manrope` (подмножества cyrillic + cyrillic-ext, все казахские буквы).
Без Google Fonts — сборка и работа не зависят от внешних CDN (важно для self-hosted в РК).

## D-008. i18n без префикса языка в URL
Язык в cookie `hs_locale` и в `profiles.locale`; переключение — server action + `router.refresh()`,
без перезагрузки страницы. Переводы разбиты по модулям: `src/messages/<locale>/<namespace>.json`.
Тест проверяет одинаковый набор ключей, валидный ICU и отсутствие нетронутых русских строк в kk.

## D-009. Версии инструментов
TypeScript 5.9 (Next 16 официально поддерживает 5.x; TS 7 — новая нативная реализация, не рискуем),
Playwright 1.56.1 (совпадает с предустановленным Chromium), @types/node 22 (под Node 22).

## D-010. RLS-тесты на Vitest + pg
Вместо pgTAP: тесты выполняют SQL в транзакции с `set local role authenticated` и `request.jwt.claims` —
ровно как PostgREST. Транзакция всегда откатывается. Отдельный тест проверяет, что RLS включён на всех таблицах `public`.

## D-011. E2E на production-сборке
Playwright запускает standalone-сборку (`scripts/serve-standalone.sh`) — тот же артефакт, что в Docker-образе.

## D-012. Параллельные модули — git worktree + отдельный локальный стек
Каждый субагент работает в своём worktree (`scripts/worktree-setup.sh <slot>`): своя БД `happysteps_s<slot>`,
свои порты GoTrue/PostgREST/шлюза и e2e-порт, `node_modules` — жёсткие ссылки (Turbopack не принимает симлинк
за пределы проекта). Точки расширения (виджеты главной, секции настроек/профиля, namespace переводов, seed)
— реестры по одной строке на модуль, чтобы слияние было тривиальным. Правила для субагентов — `docs/AGENT_GUIDE.md`.

## D-013. Уведомления: одна таблица, текст по типу
`notifications(type, params)` — текст рендерится на языке читателя из `notifications.json`, а не хранится.
Создаются только сервером (service role) после проверки прав действия — `lib/notify.ts`. Push добавляется в этапе 6
в тот же вызов `notify()`, модули менять не придётся.

## D-014. Праздники и выходные сада
Таблица `holidays` (holiday / day_off / working_day для перенесённых суббот) + `kg_is_working_day(kg, date)`.
Кнопка «Заполнить праздники РК» генерирует официальные праздники с переносом выходных; Курбан айт — по таблице дат
2025–2028 (лунный календарь), дальше заведующая добавляет вручную.

## D-015. Бизнес-ошибки из SQL
Функции и триггеры модулей бросают `raise exception 'hs:<ключ>'`; сервер показывает перевод ключа из `errors.json`.

## D-016. Локальная эмуляция Realtime
Docker-образ Supabase Realtime недоступен, поэтому шлюз локального стека эмулирует протокол Phoenix для
`postgres_changes` (`scripts/local-supabase/realtime.mjs`). Для таблиц из публикации `supabase_realtime`
создаются локальные триггеры с `NOTIFY` (только в локальном стеке; в облаке/self-hosted работает настоящий Realtime по WAL).
Каждый подписчик перечитывает строку от своего имени — RLS решает, кому доставить, как и в Supabase.
Как и в Supabase, DELETE-события содержат только первичный ключ и не фильтруются RLS — поэтому модули
используют мягкое удаление (`deleted_at`). Broadcast и Presence не эмулируются — приложение их не использует.

## D-017. Учёт рабочего времени (этап 2A)
- Единственный источник статусов — SQL `worktime_range(kg, from, to)`: дашборд, страница, табель и экспорт считают одинаково.
  Статусы: на работе / ушёл / опоздал / отсутствует / не отметился / ещё не начался / выходной + флаг «вне графика».
- «Опоздал» — первая отметка позже начала смены + порог; «Не отметился» — только после этого момента или за прошлые дни.
  Отметка в день без смены — работа вне графика, не опоздание. Если есть и отсутствие, и отметка — побеждает отметка.
- В `work_sessions` никто не пишет напрямую (даже владелец): «Начать/Закончить» — функции с серверным `now()`,
  правки заведующей — функции с обязательным комментарием (≥3 символов) и записью в журнал внутри SQL.
- Смена на дату: исключение на дату → праздники/выходные сада → недельный шаблон. Шаблон без истории: прошлые дни
  считаются по текущему шаблону, разовые изменения — через исключения и отсутствия.
- Автозакрытие: в конце смены + 2 ч открытый интервал закрывается концом смены с флагом; без смены — закрывается
  в момент начала (0 ч) после конца дня + 2 ч, чтобы неподтверждённые часы не считались — заведующая поправит.
- Архивный сотрудник остаётся в табеле за дни до архивации и за любые дни с отметками.
- Кнопка рабочего дня у владельца — только если у него есть график или отметки. PDF — шрифт DejaVu (кириллица и казахский).

## D-018. Посещаемость (этап 2B)
- Статус ребёнка за день: строка посещаемости, иначе «не придёт» по сообщению родителя, иначе «не отмечен».
  Сообщения родителей заранее помечают ребёнка, не создавая строк; воспитатель может переотметить «Был».
- Порции: ожидаемо = активные − отсутствующие (включая сообщённые); после полной отметки = пришедшие.
  Повар получает только числа (`expected_portions`), имён детей не видит.
- Группа считается отмеченной, когда у каждого ребёнка есть отметка или сообщённый пропуск (для напоминаний).
- Правки прошлых дней пишутся в журнал триггером в БД — не обойти никаким маршрутом.
- Отмена пропуска родителем — до первого дня; если период уже начался — отменяются дни с завтрашнего.
  Владелец/заведующая могут сообщить и отменить пропуск за родителя (с записью в журнал).
- Напоминание — воспитателям группы, эскалация — заведующим (если их нет — владельцу); дубли исключены записью в БД.

## D-019. Меню (этап 2C)
- Сохранение заменяет весь день одной функцией `save_menu` (с правами вызывающего — RLS действует); пустой день удаляется.
- Выключенные в настройках приёмы пищи скрыты везде; настройка приёмов пищи — только в карточке меню в настройках.
- Правки меню не пишутся в журнал (не чувствительные), изменение набора приёмов пищи — пишется.

## D-020. Объявления и события (этап 2D)
- Аудитория — одно SQL-правило для RLS и для списка получателей уведомлений: весь сад / группы (администрация +
  воспитатели групп + родители детей, которые сейчас в группе) / сотрудники. Автор всегда видит своё.
- Воспитатель публикует только своим группам (проверка на сервере и в БД). Статистика, «Напомнить», правка и удаление —
  автор, владелец, заведующая. «Напомнить» — не чаще раза в час.
- «Прочитано» ставится эффектом на клиенте после открытия (предзагрузка ссылок не отмечает прочтение).
- Файлы загружаются по одному (лимит server action), до 10 фото и 10 PDF, ≤15 МБ каждый; пути `<сад>/<объявление>/…`.
- Дни рождения: администрация и бухгалтер — все дети и сотрудники; воспитатель — дети своих групп и сотрудники;
  родитель — только свои дети; повар и педагог кружка — сотрудники.
- Напоминание о событии — накануне, после окончания тихих часов сада; при переносе даты — новое напоминание.
- Названия месяцев и дней недели — из файлов переводов, а не из браузера (в браузере kk откатывался на русский).

## D-021. Расписание cron
Задачи — маршруты `/api/cron/*` с `CRON_SECRET` (`vercel.json`). Vercel Hobby разрешает только ежедневный cron;
для демо на Hobby вызывать маршруты внешним планировщиком или `pg_cron` + `pg_net` в Supabase; на своём сервере —
системный cron (контейнер в docker-compose).

## D-022. Итоги ревью этапа 2
- Дни рождения — только в календарях администрации, бухгалтера и воспитателя (и родителю — свои дети);
  у сотрудников наружу отдаётся только день и месяц, без года рождения и возраста.
- Клиент не может задавать служебные поля при вставке (`created_at`, `reminded_*`, связь отметки с сообщением о пропуске):
  вставка разрешена только по перечисленным колонкам; связь с пропуском всегда ставит триггер.
- Файлы объявлений регистрирует только сервер (после проверки прав); путь обязан начинаться с `<сад>/<объявление>/`.
- Событие «Выходной день сада» создаёт заведующая/владелец, и оно же добавляет день в праздники/выходные сада —
  единый источник выходных для посещаемости и учёта времени.
- Отпуск/больничный не отмечаются в выходные. Напоминание «отметьте посещаемость» не уходит позже 4 часов после времени напоминания.
- Педагог кружка не видит порции и посещаемость (§3.4). Архивные воспитатели не получают уведомлений о пропусках.
- Карточка сотрудника в учёте времени разбита на вкладки (дни / график / изменения / отсутствия) — одно действие на экран.
- «Отсутствует» — пастельный розовый, отличимый от фирменного малинового; малиновый — только для главных действий.
- Маленькие кнопки на сенсорных экранах — 44px. Карточка «Требует внимания» — на этапе 5.

## D-023. Чаты
- Типы: чат группы (создаётся с группой; участники вычисляются из ролей: владелец, заведующая, воспитатели группы и родители её детей),
  общий чат сотрудников, личные чаты. Состав не хранится — уход ребёнка или архив сотрудника сразу закрывает доступ.
- Заведующая может запретить родителям писать в чат группы и удалить любое сообщение; автор правит своё сообщение 15 минут, удаляет — всегда
  (мягкое удаление: остаётся «Сообщение удалено», файлы стираются из хранилища).
- Родитель видит историю чата группы с дня, когда ребёнок пришёл в группу; сотрудники видят всю историю. Счётчик непрочитанного — с более
  поздней из дат: отметка прочтения или приход в группу.
- Тихие часы: родителю показывается предупреждение; сотрудник получает уведомление в колокольчик сразу, а push — после окончания тихих часов
  (`notifications.deliver_after`). На один чат — не больше одного непрочитанного уведомления.
- Тип файла определяется по его содержимому, а не по заявленному браузером; HEIC переводится в JPEG на устройстве.
- Realtime: после подключения канала чат догружает последние сообщения (ничего не теряется, пока канал подключался).
- Человек, который одновременно сотрудник и родитель, видит чат группы своего ребёнка как родитель, а свои рабочие чаты — как сотрудник.

## D-024. Документы
- Папка ребёнка: видят владелец, заведующая, воспитатель группы и родители ребёнка; загружают администрация и родители; родитель удаляет только своё.
- Документы сотрудника: видят администрация, бухгалтер и сам сотрудник. Срок действия — напоминания за 30 и за 7 дней (cron), по одному разу на срок.
- Новый документ того же вида (медкнижка, справка о несудимости, договор) с более поздним сроком заменяет старый: старая копия остаётся
  в папке, но больше не напоминает и не попадает в «Истекающие документы». Вид «Другое» ничего не заменяет.
- Все бакеты хранилища приватные, с ограничением размера и типов файлов; чтение — через короткие подписанные ссылки.

## D-025. Оплата: модель баланса
- Все принятые чеки ребёнка — один общий «кошелёк». Он гасит счета с самого старого месяца (FIFO), каждый — не больше его суммы.
- Долг каждого месяца живёт только в его счёте (`balance = amount − paid_amount`), поэтому итоги месяца, должники и выгрузка не считают долг дважды.
  «К оплате» для родителя = долг прошлых месяцев + текущий счёт. Переплата — аванс, его автоматически забирает следующий счёт.
- Просрочка: у счёта — свой срок оплаты; у родителя хронический долг виден как просрочка и в первые дни нового месяца.
- Начисление вручную — только за текущий месяц или предыдущий (если в саду уже есть счета того времени), с подтверждением.
- Ребёнок, пришедший в середине месяца, получает счёт в первый день посещения на полную сумму (без пропорции); счёт помечен «с ДД.ММ»,
  бухгалтер при необходимости корректирует сумму с комментарием.
- Решение по чеку можно отменить (владелец/бухгалтер, с причиной, в журнале); родителю об отмене не сообщается.

## D-026. Итоги ревью этапа 3
- Исправлены: FIFO-погашение долгов, окно ручного начисления, просрочка хронических должников, новые дети в середине месяца, отмена решения по чеку,
  тихие часы (откладывание вместо потери уведомления), история для новых родителей, тип файлов по содержимому, мягкое удаление файлов чата,
  кнопки 44px, месяц на телефоне, строчные названия месяцев во фразах, «Борышкерлер», окно правки 15 минут, замена документов, лимиты бакетов.
- Карточка «Требует внимания» (чеки на проверке, истекающие документы, ожидающие заявки) — на этапе 5.
- Параметр месяца в уведомлениях хранится как `YYYY-MM`; текст на языке читателя формирует отображение уведомлений (этап 6).

## D-027. Кружки
- Статусы записи: заявка → записан / в очереди / отклонена; записан → отписан (родитель) / исключён (администрация). Одна открытая запись
  на ребёнка и кружок, история сохраняется.
- Очередь строгая (порядковый номер). Если свободные места уже «закреплены» за ожидающими, новая заявка сразу встаёт в очередь;
  подтвердить ожидающего можно только по порядку. Все переходы — функции БД с блокировкой строки кружка; клиенты не пишут записи напрямую;
  лимит мест нельзя опустить ниже числа записанных.
- Возраст — полные годы на «сегодня» сада, включительно; проверяется и на сервере, и в БД. Каталог сада родителю виден целиком (кружки не секрет),
  фильтр по возрасту — в интерфейсе, а записаться не по возрасту нельзя.
- Подтверждают/отклоняют: владелец, заведующая или педагог этого кружка; исключают и удаляют кружки — только администрация (с журналом).
- Педагог кружка видит своих детей только через список кружка: у записанных — группа, аллергии и контакты родителей с кнопкой «Написать»;
  у заявок и очереди — только имя и возраст. Карточку ребёнка, посещаемость, документы и счета он не видит. Родитель может первым написать
  педагогу кружка, в котором занимается его ребёнок.
- Уведомления: новая заявка — заведующей (или владельцу) и педагогу; место освободилось при очереди (ушёл, исключён, ребёнок в архиве,
  выросла вместимость) — заведующей; решение — родителям. Архив ребёнка автоматически завершает его записи.

## D-028. Лист ожидания и публичная форма
- Форма `/apply/<сад>` без входа; аноним не имеет доступа к таблицам — сервер проверяет данные, ловушку для ботов и лимиты, затем пишет
  сервисной ролью. Лимиты на сад: 10 заявок в час с одного IP, 60 в час всего, 3 в сутки на телефон; повтор той же заявки не дублируется.
- IP берётся только из заголовков доверенного прокси: на Vercel — `x-vercel-forwarded-for`, на своём сервере — звено `TRUSTED_PROXY_HOPS`
  справа в `x-forwarded-for` (настраивается при развёртывании).
- Статусы свободно переключаются между «Новая», «Связались», «Отказались» (каждое изменение — в ленте заявки); «Принята» — окончательный.
- «Принять» — одна транзакция в БД (родитель, ребёнок в выбранной группе, связь, статус, журнал) по одноразовому токену захвата заявки:
  двойной клик или два администратора одновременно не создают дублей; при сбое ничего не остаётся. Приглашение родителю — после успеха.
- Ссылка и QR-код формы — на странице листа ожидания и в настройках сада; QR генерируется своим кодом без внешних библиотек.
- Ошибки на публичной форме показываются в самой форме, а не всплывающим сообщением.
